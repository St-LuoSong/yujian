# 安全与稳定性审计

日期：2026-10-04（Asia/Shanghai）
范围：后端（Spring Boot）、APK（Flutter）、管理台（Vue）、部署（Docker + 腾讯云单机）

> 这份文档回答三个问题：**现在已经挡住了什么**、**这次补了什么**、**还剩什么没挡住**。
> 每条结论都对应代码里的具体位置或一次实测，不写"应该没问题"。

---

## 一、结论摘要

系统的身份、越权、输入校验、上传与密钥保护这几条线是完整的；这次审计补上了
**接口限流**、**外部工具每日配额**和**请求体积护栏**——也就是"一个人能不能把
服务或上游额度打穿"这一类问题。

剩下**真正会挡住上线**的只有一条：**没有 HTTPS**。其余都是"多实例 / 运维"
层面的问题，不影响当前单机演示，但上线前要排期。

## 二、本轮新增

### 1. 接口限流（6 个桶）

`RequestGuardFilter` + `RateLimitService`，固定窗口计数，按主体分桶。

| 桶 | 默认 | 作用 |
| --- | --- | --- |
| `auth` | 10 次 / 60 秒 | 防撞库与验证码轰炸 |
| `plan` | 20 次 / 60 秒 | 防一次会话里连点生成 |
| `plan-daily` | 60 次 / 24 小时 | **大模型开销的硬上限** |
| `media` | 30 次 / 60 秒 | 上传会落盘并重编码，比普通请求贵 |
| `write` | 60 次 / 60 秒 | 点赞、收藏、评论等 |
| `read` | 300 次 / 60 秒 | 正常浏览远到不了这个数 |

几个刻意的决定：

- **主体按账号优先、IP 兜底**：登录用户用 user id（不可伪造），匿名才用 IP。
- **`X-Forwarded-For` 只在直连方是内网时才采信**。公网直连的场景下任何人都能
  伪造这个头，无条件信任等于把限流做成摆设。
- **`plan-daily` 用长窗口而不是计数器**：同一个限流器换个窗口长度就得到了
  "每日上限"，不需要为成本控制再写一套东西。
- 超限返回 **429 + `Retry-After`**，客户端据此决定何时重试，而不是盲目重试。

### 2. 外部工具每日配额（3 组）

`ToolQuotaService`，在 `ToolOrchestrator.measure()` 这个**唯一的外部调用汇聚点**上拦截。

| 组 | 默认 | 覆盖的工具 |
| --- | --- | --- |
| 天气 | 500 / 天 | `getWeather`（含"第 N 天"的变体） |
| 路线 | 300 / 天 | `getRoute`（百度地图） |
| 铁路 | 300 / 天 | `searchTrain` / `quoteRailFares` / `searchTransfer` |

三个关键决定：

1. **不新建计数表**，直接用 `tool_invocation_log` 统计。理由是它本来就逐次记录
   每次调用，而"自己维护一个计数器"最容易出的问题就是重启后清零 —— 那样限额
   会在每次部署后重新发放一遍。为此补了 `(tool_name, created_at)` 索引。
2. **只限制外部工具**。景点检索、开放时间、门票价格读的是我们自己的内容库，
   没有第三方额度可烧。
3. **额度用尽时熔断，而不是偷偷换成演示数据**。返回带 `TOOL_QUOTA_EXCEEDED`
   的错误结果，走既有的"未取到实时数据"提示链路。把兜底数据说成实时数据，
   是这个项目从头到尾都在避免的事。同时**不记入工具健康度**——工具没坏，
   是我们主动停的。

### 3. 请求体积护栏

审计中发现的实际缺口：`max-http-form-post-size` 只管表单，**JSON 请求体没有
容器级上限**，一个几百 MB 的 body 会被直接读进内存。现在非 multipart 请求
超过 1 MB 直接 413。上传走 multipart，由各自的业务上限（8 MB / 300 MB）管。

### 4. 运营台可调

新增「安全与限流」页（`/security`）。额度、窗口、总开关都能在线改，改完立刻生效，
并且能看到**今日已用量与进度条**——"什么时候该收紧"是运营看着用量决定的事，
不该每次改环境变量重启服务。

配置落在 `app_setting` 表，只接受登记过的键（`SecuritySettings` 白名单），
范围之外的取值当场拒绝。比如把读接口上限写成 0 会被驳回，而不是先存下来
把接口全锁死。

## 三、已经到位的控制项

| 面 | 措施 | 位置 |
| --- | --- | --- |
| 口令 | BCrypt 哈希，不存明文 | `AuthService` |
| 会话 | 短时 access token + 可撤销 refresh token（存哈希） | `JwtService` / `RefreshToken` |
| 改密 | 改密后撤销该账号全部 refresh token | `AuthService.changePassword` |
| 越权 | 行程 / 收藏 / 旅记按归属校验；评论删除越权返回 **404 而不是 403** | `TripPlanService` / `CommunityService` |
| 角色 | `/api/admin/**` 需要 ADMIN 角色 | `SecurityConfig` |
| 输入 | Bean Validation + 服务端二次校验（长度、范围、枚举白名单） | 各 `*Models` + Service |
| 上传 | 只认文件头魔数、服务端生成 UUID 文件名、路径穿越防护、重编码去 EXIF、尺寸与大小上限 | `MediaStorageService` |
| 密钥 | 百度 AK / LLM Key / SMTP 只在服务端环境变量，APK 与管理台都不持有 | `AppProperties` + compose |
| 日志 | 不记 token、密码、完整敏感请求；工具日志只存摘要 | `OperationLogService` / `ToolOrchestrator` |
| 数据最小化 | 不采身份证、银行卡、支付信息、后台持续定位 | 全项目 |
| 结构 | Flyway 版本化迁移，生产 `ddl-auto=none` | `db/migration` |
| APK 更新 | 双通道 + 签名校验 + 版本跨度强制更新 | `AppReleaseService` |

## 四、剩余风险

### P0 — 上线前必须解决

**1. 没有 HTTPS。**
Debug APK 走明文 HTTP，登录口令、access token、行程内容在网络路径上是明文。
同一网络里的任何人都能读到 token 并冒充用户。
演示环境可以接受（评委在受控网络里操作），**真实用户不能**。
做法：Caddy + 域名（自动证书）或证书直接挂到现有入口，然后在
`--dart-define=API_BASE_URL=https://...` 下打包 release 包。

### P1 — 多实例或长期运行前要处理

**2. 限流与设置缓存都是单进程内存态。**
多实例部署时每个实例各限一份，实际总放行量会翻倍；`app_setting` 的改动也要
等各实例自己过期。当前是单机部署，够用；要水平扩展时这两处换成 Redis。

**3. 没有数据库备份。**
MySQL 在 Docker 卷里，没有自动备份策略。一次误操作（比如 `docker compose down -v`）
会连带用户、行程和运营台录入的景点一起丢。至少要有每日 `mysqldump` 到对象存储。

**4. 没有外部监控与告警。**
现在只有容器 healthcheck 自愈。服务反复重启、外部工具大面积失败、额度用尽
这些事件，没人会被告知。运营台的「AI 运行」「安全与限流」两页能看到现状，
但需要有人主动去看。

### P2 — 值得知道，暂时可以不改

**5. 管理台 token 存在 localStorage。**
一旦管理台出现 XSS，token 可以被读走。当前管理台是内部使用、内容都由自己录入，
但上线前建议加一条 CSP 头。

**6. 体积护栏只看 `Content-Length`。**
分块传输（chunked）的请求没有这个头，能绕过这道检查。Tomcat 自身的
`maxSwallowSize` 仍然兜底，但如果要严格，需要换成计数包装的输入流。

**7. 大模型的 token 用量没有上限。**
`plan-daily` 限的是**次数**，不限单次输入的**长度**。一个超长 prompt 仍然
可能产生一笔不小的账单。要做的话，是在调模型前按字符数粗估并拒绝。

**8. 匿名用户按 IP 限流。**
同一个 NAT（学校、公司、展会 Wi-Fi）后面的所有游客共享一份额度。展会现场
如果很多人同时用，可能被人多的那个出口先把额度吃掉。要不要为匿名放宽，
是产品判断，不是技术问题。

## 五、验证记录

### 限流（线上实测）

```text
连续 12 次错误口令登录（auth 桶 10 次/60 秒）：
401 401 401 401 401 401 401 401 401 401 429 429

第 11 次的响应体：
{"code":"RATE_LIMITED","message":"请求过于频繁，请 60 秒后再试","bucket":"auth"}

同一时刻读接口不受影响：GET /api/pois → 200
管理端接口未带管理员身份：GET /api/admin/security/limits → 401
```

### 请求体积护栏（线上实测）

```text
POST /api/feedback，body 约 2 MB（JSON）
→ status=413  {"message":"请求内容过大","code":"PAYLOAD_TOO_LARGE"}

正常请求不受影响：GET /api/pois → 200
```

### 工具配额（线上实测）

```text
GET /api/admin/security/limits（管理员身份）：
activeWindows = 4
weather 天气（Open-Meteo）      used = 0  limit = 500
route   路线（百度地图）        used = 0  limit = 300
rail    车次与票价（12306）     used = 0  limit = 300
```

`used = 0` 是正确结果：前一天的工具调用不属于今天（按 Asia/Shanghai 自然日切分）。

## 六、运营手册：什么时候该动哪个数

| 现象 | 动作 |
| --- | --- |
| 上游提示额度将尽 | 「安全与限流」里把对应组的每日上限调低，而不是等服务端自己撞墙 |
| 某个外部源大面积失败 | 工具健康度页确认后，可临时把该组配额调到很低以停止无效请求 |
| 有人刷接口 | 看 429 的桶名，收紧对应桶；`plan-daily` 用于压成本 |
| 排查时被自己的限流挡住 | 把「接口限流总开关」置 0，排障完立刻打开 |
| 参数改乱了 | 点「恢复默认」，所有项回到登记表里的默认值 |
