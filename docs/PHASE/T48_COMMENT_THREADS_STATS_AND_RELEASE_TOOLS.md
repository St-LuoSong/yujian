# T48：二级评论与评论点赞、互动数据、发布管理补齐

日期：2026-10-03（Asia/Shanghai）

## 一、二级评论

`community_comment` 增 `parent_id`（可空）与 `like_count`。

- **只做两层**：回复的回复一律收敛到同一条顶层评论（服务端 `resolveReplyTarget`
  会往上找一层）。手机屏幕上三层以上的缩进会先把正文挤没。
- **删顶层评论会带走它的回复**：外键写成 `on delete cascade`，同时把它们的计数
  一起从 `comment_count` 里扣回来 —— 留下 `parent_id` 指向已删行的孤儿回复，
  界面上既显示不出来也删不掉。

### 折叠规则

回复超过 **3 条**自动进入折叠态，只露前三条，下面出现「展开另外 N 条回复」；
展开后同一个位置变成「收起回复」。

### 通知

收件人优先是"被回复的那条评论的作者"，没有父评论时才是旅记作者。发给自己的不发；
但如果"回复自己"发生在别人的旅记下，旅记作者仍然会收到，因为那确实是一条新留言。

## 二、评论点赞

新表 `community_comment_like`（`user_id` + `comment_id` 唯一）。

与旅记点赞分开存：合表之后"这个 id 是旅记还是评论"得靠一个类型列去区分，
唯一约束和外键也都没法各自生效。

**接口只回那一条评论**（`replies` 恒为空），客户端只取 `likeCount` 与 `likedByMe`
写回树里：拿返回值整棵替换会把回复列表清空。这一条在客户端的注释里也写了。

## 三、「我的」页互动数据

新接口 `GET /api/community/stats/me`，四个数字：

| 字段 | 含义 |
| --- | --- |
| `postLikes` | 我的旅记收到的点赞 |
| `commentLikes` | 我的评论收到的点赞 |
| `favorites` | 我的旅记被收藏的次数 |
| `comments` | 我发表过的、仍然可见的评论数 |

**每个计数都带 `user.id <> :userId` 的条件**：自己给自己的旅记点赞、给自己的
评论点赞都不算"获得"。少了这一条，这块数据就退化成"我点过多少下"。

界面上做成梯度深色卡（四个数字 + 标签），数字用 `FittedBox` 收窄 ——
六位数在 1.3 倍字号下会比那一格还宽。

## 四、管理台

### 评论管理

旅记审核抽屉里新增评论区：正文直接摊开显示（折叠在审核场景只会多两次点击），
每条带「隐藏 / 恢复」，回复缩进挂在父评论下。隐藏不删行，保留复核的余地。

隐藏顶层评论会连带隐藏它的回复：只藏父评论的话，那些回复会既算在
`comment_count` 里、又因为父评论不可见而在界面上消失。

### 重新发布

`PATCH /api/admin/app-releases/{id}/restore`，管理台在「已停用 / 已替代」的行上
显示「重新发布」按钮。

只能**往上恢复**：已有更高的公开版本时直接拒绝，并说明原因 —— 把客户端推回
老包不是"恢复"，是事故。

## 五、更新后的消息通知

- `user_message` 增 `dedupe_key`，与 `user_id` 组成唯一索引。
- 客户端启动（或从后台回到前台）时调用 `POST /api/app-releases/ack`，带上自己
  当前的包名、versionCode 与通道。
- 服务端找到对应版本的发布记录后，用 `APP_RELEASE:<id>` 作去重键往消息中心写
  一条通知，正文就是管理员在后台填的更新说明。

**为什么必须去重**：客户端每次启动都会 ack 一次，没有去重键的话，用户会在消息
中心里攒下一整列内容相同的"已更新到 vX"。实现上是"先查再写 + 唯一索引兜底"
两层：只靠查询会被并发绕过，只靠唯一索引会把一次正常回执变成 500。

未登录时 ack 返回 204 而不是 401：这是启动时的顺手动作，让游客在后台刷出一条
鉴权失败毫无意义。

## 六、发现页头像不同步

`_HeaderAvatar` 之前只画用户名首字，完全没看 `avatarKey` 和 `avatarUrl` ——
所以换了头像首页不变。现在按 **上传的照片 → 预设图案 → 首字** 取，
地址由 `AppConfig.resolveMediaUrl` 补全。

## 九、真机踩到的通道 bug（2026-10-03 23:20 修复）

**现象**：管理台发布了 v0.5.0（通道=调试、versionCode 5、最低支持 3），
手机上 v0.4.0 点「检查更新」却提示"服务端暂未发布"。

**根因**：`AppUpdateRepository.check()` 从一开始就**没有把 `channel` 发给服务端**，
只发了 packageName 与 versionCode。服务端收不到通道参数就按正式通道查，
而发布的是调试包 —— 两条通道互不相通，于是永远查不到。
`acknowledge()` 当时带了 channel，`check()` 漏了，两个方法的参数集不一致才让这个
bug 藏了整整一轮。

**修复**（两层，缺一不可）：

1. 客户端 `check()` 带上 `channel = debuggable ? DEBUG : RELEASE`；
   补了一条专门盯这个点的回归测试。
2. 服务端给**已经装出去的 v0.4.0 及以前**留过渡口子：
   `channel` 参数缺失（注意不是显式传 RELEASE）时，先查正式通道，
   正式通道没有已发布版本才回落到调试通道。
   由 `APP_RELEASE_LEGACY_DEBUG_FALLBACK` 控制，默认开，用完应该关掉。

   > 之所以要第二层：v0.4.0 装在用户手机上，客户端代码改不动。只修客户端的话，
   > 那份 APK 会被永久锁死，只能手动重装。缺省值之所以是"回落到调试"而不是
   > "跨通道任选"，是因为前者只在"正式通道空、调试通道有包"时生效 ——
   > 正式包用户本来在那条通道上什么也拿不到，最坏情况不会变差。

**验证**（服务器本机）：

```text
不带 channel      → releaseAvailable:true,  latestVersionCode:5, 0.5.0
channel=DEBUG     → releaseAvailable:true,  latestVersionCode:5, 0.5.0
channel=RELEASE   → releaseAvailable:false
```
