# 人工智能工具使用说明

**作品名称**：豫见智旅　**参赛赛道**：移动与网络应用开发

## 声明

本作品的全部创意、选题、产品定位、功能设计、信息架构、交互方案与视觉方向，**均由队伍成员独立提出并决策**。人工智能工具在本项目中仅作为**辅助实现手段**参与代码编写、缺陷调试与应用测试，不参与作品构思与设计决策，也未替代团队对内容的判断与把关。

本文如实说明所用工具、使用环节、工作流程、输入素材与关键参数，并区分两类完全不同的 AI 使用：

| 类别              | 含义                     | 是否属于作品本身      |
| --------------- | ---------------------- | ------------- |
| **开发期 AI 辅助工具** | 团队在写代码、查缺陷时使用的编程助手     | 否，是工具，不进入作品运行 |
| **产品内集成的生成式模型** | 作品运行时调用的大语言模型，用于生成行程方案 | 是，作品的功能组成     |

## 一、开发期使用的 AI 辅助工具

### 1.1 工具与用途

| 工具                            | 形态      | 使用环节                         |
| ----------------------------- | ------- | ---------------------------- |
| Codex（OpenAI）                 | 命令行编程助手 | 代码生成与修改、缺陷定位、重构、单元测试编写、文档草稿  |
| Deepseek V4.1-flash（DeepSeek） | 代码评审助手  | 变更评审（可维护性 / 边界情况 / 回归风险三个维度） |

### 1.2 主要工作流程

全程采用**团队驱动、AI 执行、团队验收**的循环，AI 产出必须经团队验证才能进入代码库：

```text
① 团队提出需求与验收标准（含手绘布局、界面截图、预期行为）
        ↓
② AI 生成代码初稿或修改方案
        ↓
③ 团队在本机与 Android 模拟器 / 真机上实际运行验证
        ↓
④ 团队反馈问题（截图、报错、复现步骤、设计意见）
        ↓
⑤ AI 定位原因并修正 → 回到 ③ 直到通过
        ↓
⑥ 团队复核确认后合入
```

交互界面几乎每一轮都经过"真机截图 → 团队指出问题 → 修改 → 再验证"的迭代（例如行内溢出、按钮对比度、下拉框样式、状态更新不渲染等）。判断标准由团队给出，AI 只负责实现与修正。

### 1.3 输入素材

提供给 AI 工具的输入**限于项目自身的代码与工程信息**：

- 本项目源码（Flutter / Java / TypeScript）与既有的设计令牌、组件规范文档；
- 团队提供的**界面截图**与手绘布局示意，用于说明期望的视觉与交互效果；
- 运行日志、接口返回、模拟器截图等调试信息；
- 团队整理的需求条目与验收清单。

**未向 AI 工具提供**：真实用户个人信息、身份证件、支付信息、第三方密钥、未公开商业数据。API 密钥只在团队本机的 `scripts/local.env`（已被 `.gitignore` 忽略）中配置，不进入对话、不进入代码库。

### 1.4 关键参数

- 使用方式：交互式逐轮迭代，**无自动化批量生成**；
- 生成粒度：单次聚焦一个功能点或一个缺陷，避免大范围不可控改动；
- 上下文约束：以本仓库源码为唯一事实来源，不引入与本项目无关的框架或依赖。

## 二、产品内集成的生成式模型

这是**作品的功能组成**，不是开发工具。模型只负责"理解需求并生成结构化行程"，其余全部由服务端代码负责。

### 2.1 模型与选型

通过 LangChain4j 统一适配四家 OpenAI 兼容供应商，按优先级依次尝试，**任一可用即返回**：

| 供应商            | 默认模型             | 优先级 | 用途               |
| -------------- | ---------------- | --- | ---------------- |
| OpenAI         | `gpt-4o-mini`    | 10  | 需求理解与行程生成        |
| DeepSeek       | `deepseek-chat`  | 20  | 同上（实际演示主力）       |
| Kimi（Moonshot） | `moonshot-v1-8k` | 30  | 同上               |
| 通义千问           | `qwen-plus`      | 40  | 同上               |
| Mock 引擎        | 规则引擎（非 AI）       | 兜底  | 全部供应商不可用时保证流程可演示 |

多供应商并行适配的用意：不把作品绑死在单一模型上，任一家限流或故障时仍可完成演示。

### 2.2 关键参数

```text
temperature      = 0.3     偏低，追求稳定与可复现，避免行程细节随机漂移
timeout-seconds  = 60      单次生成超时上限
输出格式          = 结构化 JSON，由服务端解析为行程模型
提示词版本        = 入库管理（prompt_version 表），运营台可发布 / 启用 / 回滚
```

每次生成的行程都会记录**实际使用的引擎与提示词版本**，可在"方案依据"页查看。

### 2.3 模型职责边界（重要）

作品刻意**不让模型承担它不该承担的事**：

| 由模型负责         | 由服务端代码负责            |
| ------------- | ------------------- |
| 理解自然语言需求、抽取条件 | 参数校验与缺失条件追问         |
| 生成结构化行程与推荐理由  | 开放时间校验、时间冲突检测       |
| 处理用户的局部调整指令   | 路线与距离校验、预算计算、行程强度计算 |
| —             | 风险识别、结构化结果落库、失败降级   |

模型**不参与**：购票、支付、预约、身份认证、交通安全承诺，也不会对实时数据作无依据承诺。

### 2.4 工具调用（MCP / 外部数据）

模型生成方案所依据的外部数据，全部由**服务端编排后注入**，客户端不直连任何外部服务：

| 工具                                                  | 数据源         | 用途          |
| --------------------------------------------------- | ----------- | ----------- |
| `searchPoi` / `checkAttractionOpening`              | 运营台内容库      | 景点与开放时间     |
| `getWeather`                                        | Open-Meteo  | 逐日天气与降水概率   |
| `getRoute`                                          | 百度地图 Web 服务 | 市内路线距离与耗时   |
| `searchTrain` / `quoteRailFares` / `searchTransfer` | 12306 MCP   | 车次、余票、票价、中转 |
| `quoteTicketPrices`                                 | 内容库参考价      | 门票预算        |

外部调用设有**每日配额**（天气 / 路线 / 铁路三组，运营台可调），额度用尽时熔断并如实标注"未取到实时数据"，不会继续消耗上游额度。

### 2.5 生成内容的标识

所有模型产出与外部数据都带**明确的状态标识**，界面逐条展示，不把生成内容冒充为核验事实：

```text
AI 生成 · 实时数据 · 缓存数据 · 系统资料 · 演示数据 · 演示数据（降级）· 数据已过期
```

- 模型生成的行程：标注 `AI 生成`；
- 外部接口实时取回的：标注 `实时数据`，并附来源与查询时间；
- 取不到而降级的：标注 `演示数据（降级）`，并在方案提示中说明原因；
- 断网时的本地缓存：标注 `缓存数据` 与更新时间。

## 三、团队实质性贡献

下表区分"团队完成"与"AI 辅助"，用于说明原创构思、内容控制、技术实现、交互设计与成果整合的实际归属。

| 环节        | 人（队伍成员）                                                                         | AI 辅助                                               |
| --------- | ------------------------------------------------------------------------------- | --------------------------------------------------- |
| **选题与创意** | 选定"河南自由行 + AI 规划"方向与作品名《豫见智旅》；确定"不做聊天机器人，要做可执行方案"的核心主张                          | 无                                                   |
| **需求分析**  | 定义目标用户（省内 1—3 日自由行游客）、三条示范走廊、首版范围与不做清单                                          | 无                                                   |
| **产品设计**  | 四 Tab 信息架构、免登录体验路径、规划闭环（发现→需求→生成→依据→调整→保存→执行）、AI 职责边界                           | 无                                                   |
| **交互设计**  | 全部页面布局与交互方案：起终点交换、中文日历、兴趣自定义、行程时间轴、地图与时间轴联动、评论折叠规则                              | 按方案实现；样式与体验由团队逐轮验收并给出修改意见                           |
| **视觉方向**  | 确定"现代中原文化 × 山河旅行影像"方向与配色（中原青黛 / 古建朱砂 / 麦穗金 / 宣纸白）；提供 Logo 与图标素材；**判定每一版界面是否达标** | 按团队给出的方向与设计令牌产出实现稿；被判定"AI 味过重""组件边界生硬"的方案由团队否决并要求重做 |
| **技术实现**  | 技术选型（Flutter + Spring Boot + MySQL + Vue）、数据分层与降级口径、安全与合规要求                     | 编写与修改代码、定位缺陷、重构、补充测试                                |
| **内容控制**  | 景点内容、文案口径、数据来源说明、图片来源与授权登记要求                                                    | 无，内容由团队与运营台维护                                       |
| **测试验收**  | 每轮在本机与 Android 模拟器/真机实测，提供截图与复现步骤，判定是否通过                                        | 编写单元测试与回归测试；按反馈修复                                   |
| **系统整合**  | 决定部署形态、演示口径（在线/稳定两套）、交付范围                                                       | 按指示完成构建与配置                                          |
| **成果把关**  | 最终判断功能是否达成、是否满足比赛要求                                                             | 无                                                   |

**一句话概括**：AI 承担的是"把已定方案写成代码"和"按反馈修缺陷"，**不承担**想做什么、给谁用、长什么样、什么算合格。

### 3.1 人工筛选与修改过程

AI 产出的内容不会直接采用，团队按以下方式处理：

- **筛选**：只接受符合本项目设计规范与验收标准的改动，不采纳引入无关依赖或超出范围的实现；
- **重构**：对实现方式提出返工要求（例如要求把重复逻辑抽成公共组件、把散落的数据状态判断收敛到单一入口）；
- **改写**：界面文案、提示语、错误信息全部按团队口径重写，确保与"如实标注数据来源"的原则一致；
- **整合**：由团队决定各模块如何拼接成完整交付物，并实际跑通端到端流程；
- **回归**：每次修改后重新运行测试与真机验证，确认没有破坏既有功能。

### 3.2 素材加工（重绘与二次创作）

本项目**不涉及影视、动画等视频素材**，因此没有剪辑环节；涉及的素材加工均在图像层面，全部由团队主导：

| 素材                           | 来源            | 加工过程                                                            |
| ---------------------------- | ------------- | --------------------------------------------------------------- |
| 应用 Logo                      | 团队自行设计并提供源图   | 裁切为方形自适应图标与启动页图，按 Android 密度规范输出 5 档尺寸；生成自适应图标前景时按安全区（68dp）重新定位 |
| 功能图标（点赞 / 收藏 / 评论 / 上传 / 举报） | 团队提供统一风格的 PNG | 统一尺寸与透明通道；**点赞与收藏的填充态由团队定义规则**，以描边版为基准做轮廓闭合与填充生成"选中"状态          |
| 河南省底图                        | 团队提供素材        | 用于"足迹"点亮展示，随应用打包                                                |

上述加工均为**同一套视觉规则下的衍生制作**，不涉及对第三方作品的复制或改写；素材来源与授权情况记录在 `THIRD_PARTY_NOTICES.md` 与《配图作业单》。

## 四、版权、数据与合规

### 4.1 版权

- 业务代码为本项目原创；第三方开源依赖的许可证逐项登记在 [`THIRD_PARTY_NOTICES.md`](../../THIRD_PARTY_NOTICES.md)；
- 优先选用 MIT / BSD / Apache-2.0 等宽松许可证依赖；对许可证不明确或已停维护的第三方地图插件，**只做研究、不引入代码**；
- Logo 与应用图标由团队提供素材制作；
- **景点配图当前为占位示例图，界面上明确标注"非河南实景"**，正式素材需经团队逐张核验授权后由运营台上传，并在内容库登记来源与授权说明（见《配图作业单》）。

### 4.2 数据与隐私

作品遵循**数据最小化**原则，明确不采集以下信息：

- 身份证号、银行卡号、支付信息；
- 与旅行无关的精确住址；
- 后台持续定位与位置历史；
- 用户通讯录；
- 相册的全量读取（仅在用户主动发布旅记、上传头像时读取**用户所选的那张图片**）。

| 场景   | 处理方式                                 |
| ---- | ------------------------------------ |
| 定位   | 仅用户主动开启"附近景点"时请求一次，坐标不缓存、不落库         |
| 图片上传 | 服务端重新编码并**剥除 EXIF**（含拍摄位置），文件名由服务端生成 |
| 密码   | BCrypt 哈希存储，不保存明文                    |
| 分享   | 只读链接，可设置有效期与隐藏预算，不含账号敏感信息            |
| 匿名体验 | 只保存令牌哈希与规划次数，不留设备追踪标识                |
| 删除权  | 用户可删除行程、收藏、关闭分享、删除账号                 |

### 4.3 肖像、声音与生物特征

本作品**不采集、不生成、不使用**任何人的肖像、声音或生物特征数据；未使用人脸识别、声纹克隆、AI 换脸或语音合成技术。

### 4.4 内容安全与伦理

- 社区旅记采用**先审后发**：用户发布内容进入待审核队列，由运营台人工审核后方可公开；
- 提供举报入口，管理员可下架违规内容并通知作者；
- 生成内容只围绕旅行规划，不涉及政治敏感、暴力、色情或误导性信息；
- 不对未核验的实时数据作承诺，不把演示数据宣称为真实数据——这是本作品贯穿始终的原则；
- 不进行诱导消费：门票为参考价，购票引导至官方渠道，平台内不完成支付。

### 4.5 密钥与接口安全

- 地图 AK、模型 API Key、SMTP 凭据**只保存在服务端环境变量**，客户端与管理台均不持有；
- API 密钥不进入代码库、不进入本文档、不进入对话记录；
- 服务端对接口分桶限流（登录、生成行程、上传、写操作、读接口），外部工具调用另有每日配额；
- 行程、收藏、旅记等数据均做**归属校验**，越权访问返回 404 而非暴露资源是否存在。

## 五、边界说明

为避免夸大或遗漏，以下内容**由团队完成，且未由 AI 代为决策**：

- 作品选题、名称、定位与核心主张；
- 全部功能设计与交互方案；
- 视觉方向、配色体系、Logo 与图标素材的确定，以及每一版界面的验收与否决；
- 景点内容、文案口径与数据来源说明；
- 手动测试、真机验收与问题判定；
- 演示脚本、答辩思路与最终成果整合。

视觉与界面部分的实际情况是：**方向、设计令牌与验收标准由团队给出，实现稿由 AI 产出后交团队评审**。团队在迭代中多次否决"AI 味过重""组件边界生硬""信息层级不清"的方案并要求重做——这一类判断与取舍是作品视觉质量的实际来源。
