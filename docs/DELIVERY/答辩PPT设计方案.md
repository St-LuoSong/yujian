# 豫见智旅 · 答辩 PPT 设计方案

> 适用场景：移动与网络应用开发赛道答辩。
> 总页数 18 页，讲授 8 分钟，问答 3 分钟。
> 每页给出：屏幕文字（直接上屏）、视觉与版式（怎么做）、口播要点（怎么讲）。

## 0. 使用说明

三条硬规则：

1. **一页只讲一件事。** 18 页里没有一页是"功能罗列"，每页的标题就是这一页的结论。
2. **屏幕上的字要少，讲出来的话要实。** 屏幕上只留短语、数字和界面截图；
   解释、因果、取舍放在口播里。评委看的是屏幕，信的是你的解释。
3. **不夸大、不含糊。** 实时数据标"实时"，演示数据标"演示"，
   没做的能力明确说"首版未做"。这与 APK 内部的数据状态标注是同一套口径，
   答辩话术和产品行为一致，本身就是加分项。

## 1. 视觉与版式规范

### 1.1 色彩（与 APK 同一套 token）

| 用途 | 色值 | 说明 |
| --- | --- | --- |
| 主色 · 品牌深青 | `#145D55` | 标题、章节条、强调块 |
| 深色 · 青黛 | `#1C4B46` | 封面底、大色块 |
| 强调 · 窑变朱 | `#C94D36` | 关键数字、风险、重点结论 |
| 点缀 · 麦穗金 | `#E8B45B` | 少量装饰，不写小字 |
| 文字 · 麦穗金深 | `#8C6A1F` | 需要读清的金色小字（价格等） |
| 底色 · 雾白 | `#F4F8F6` | 正文页底 |
| 正文 · 墨 | `#16211F` | 主文字 |
| 次要 · 雾灰 | `#73817C` | 注释、来源 |

**不要做的事**：满屏古风纹样、默认模板蓝紫渐变、每一页都放无关装饰图、
用一张拼贴大图替代架构说明。河南地域感靠**真实景区影像 + 克制的青黛朱砂**，
不靠纹样。

### 1.2 字体与网格

- 中文标题：思源宋体 / 方正小标宋（一页一个），字号 32–40；
- 中文正文：思源黑体 Regular，字号 18–20；
- 数字与英文：与正文同族的 Latin 部分，数字用等宽（tabular）对齐；
- 版心：16:9，左右留白 = 版心宽的 6%，正文最多 6 行；
- 统一参考线：所有页面标题同一高度，右下角固定放页码 + 项目名。

### 1.3 截图与图表规范

- 截图统一用**模拟器竖屏 + 手机外框**，不带桌面背景、不带鼠标指针；
- 一张页面图只出现一次，重复使用的页面用局部放大（卡片 / 时间轴 / 校验结果）；
- 数据图表只做四类：预算拆分（横向比例条）、行程强度（三档刻度）、
  外部工具来源与耗时（状态条）、版本发布通道（流程图）；
- 每个图表都带**时间范围 + 数据来源 + 更新时间**，与产品内一致；
- 架构图用同一套色，连线不用红色（红色留给风险）。

## 2. 逐页方案

### 第 1 页 · 封面

- **屏幕文字**：
  - 主标题：豫见智旅
  - 副标题：面向河南自由行游客的 AI 旅行规划与智慧出行平台
  - 底部：队伍名称 / 成员 / 指导教师 / 日期
- **视觉**：满版河南山河实景照，压 60% 青黛遮罩；标题居左下，
  右侧竖排放 APK 图标。不放动画。
- **口播（≈20s）**："我们的作品叫豫见智旅，'豫'是河南，'见'是遇见，
  一句话概括：让游客把'想去河南'变成一份走得通的行程。"

### 第 2 页 · 问题：河南自由行难在哪

- **屏幕文字**（三条，每条一行结论）：
  1. 攻略散：图文、短视频、笔记，信息在不同平台，看完仍然不知道**怎么排**；
  2. 串不起来：郑州—洛阳—云台山之间是高铁、城际还是自驾，跨城与市内接驳没人替你算；
  3. 不敢信：开放时间、门票、天气随时变，AI 写的行程**看着美，走不通**。
- **视觉**：左侧三条结论，右侧一张"信息碎片"合成图
  （多个平台截图叠在一起 → 打叉）。不要放竞品 logo。
- **口播（≈35s）**：强调第三点是我们的切入点 —— 通用聊天机器人不缺文案能力，
  缺的是**可执行性校验**。

### 第 3 页 · 目标用户与核心场景

- **屏幕文字**：
  - 核心用户：首次来河南的 1–3 日自由行游客 + 河南本地周末短途游客；
  - 典型诉求：两人、周末、郑州出发去洛阳、想看历史文化、人均 1000、别太累；
  - 首版聚焦：郑州—开封、郑州—洛阳、焦作—云台山三条示范走廊。
- **视觉**：三条走廊做成横向卡片（照片 + 主题标签 + 天数），
  中间放"用户一句话 → 系统理解"的小对照。
- **口播（≈30s）**：明确说"我们**故意不做**全省铺量"，
  先把三条走廊做深，这是范围控制而不是能力不足。

### 第 4 页 · 产品定位：不是攻略浏览器，也不是聊天机器人

- **屏幕文字**：
  - 河南文旅内容探索 + AI 旅行规划 + 路线与交通协同 + 行程执行辅助；
  - 关键差异：**LLM 不负责拍板，后端负责校验**。
- **视觉**：一张四象限图（传统攻略 / 通用 AI 对话 / 我们），
  横轴"内容可信度"，纵轴"可执行性"。
- **口播（≈25s）**：一句话讲清赛道定位：我们做的是**行程的生产线**。

### 第 5 页 · 交付形态与整体架构

- **屏幕文字**：
  - Flutter Android APK（主交付，面向游客）
  - Spring Boot 服务端（业务 / AI 编排 / 工具适配 / 数据安全）
  - Vue 3 管理台（内容、资源、配额、版本发布、审核）
  - MySQL 8 + Flyway（V1–V6 迁移，云上容器化部署）
- **视觉**：三端架构图；下方一条数据流：
  `APK → Spring Boot → {LLM, 百度地图, 12306 MCP, Open-Meteo} → MySQL / 缓存`。
  在图上直接标出"**第三方密钥只在服务端**"。
- **口播（≈40s）**：重点讲"前端不直连第三方"的原因：
  反爬与频率限制、AK 泄露风险、统一缓存与降级。

### 第 6 页 · 功能地图

- **屏幕文字**：底部四个一级入口 + 三条能力线：
  - 发现：景区卡片、主题路线、文化锦囊、附近景点；
  - 规划：一句话需求 → 必要追问 → 确认摘要 → 生成 → 调整 → 撤销；
  - 行程：时间轴、地图、预算、天气、今日行程与下一站；
  - 我的：收藏总站、我的行程、消息、设置、足迹；
  - 社区（行后）：图文旅记、点赞、收藏、评论与二级评论、举报与审核。
- **视觉**：中间放 APK 四屏首页截图，四周用细线引出子功能；
  不用"功能列表"式的项目符号堆满整页。
- **口播（≈35s）**：一句话带过覆盖面，把时间留给后面的闭环和校验。

### 第 7 页 · 核心闭环：行前 → 行中 → 行后

- **屏幕文字**：
  - 行前：一句话需求 → 结构化行程（含依据）；
  - 行中：今日行程 / 下一站 / 实时天气与交通；
  - 行后：行程留存为足迹 + 社区分享；
  - 一条贯穿：**每个数据点都标来源与状态（实时 / 缓存 / 系统资料 / 演示）**。
- **视觉**：一条从左到右的时间轴，三个节点各配一张局部截图；
  时间轴下方用四色小方块表示数据状态，与产品界面上的标识一一对应。
- **口播（≈35s）**：这一段是全场主线，后面第 8–11 页都在展开它。

### 第 8 页 · AI 规划：职责边界

- **屏幕文字**：
  - LLM 负责：理解自然语言、识别缺失条件、生成结构化行程、解释推荐理由、处理局部调整；
  - 后端负责：参数校验、开放时间校验、时间冲突、路线与距离、预算、行程强度、风险识别、结构化落库；
  - LLM 不做：购票、支付、预约、身份认证、对实时数据作无依据承诺。
- **视觉**：左右分栏的"职责边界"表；中间一条竖线，线上标注
  "结构化输出（Schema 校验）"。
- **口播（≈40s）**：这是我们最想讲清的一点 ——
  **让模型做它擅长的语言工作，让代码做它擅长的规则工作**。

### 第 9 页 · 技术路线：多供应商 LLM + 工具编排

- **屏幕文字**：
  - LLM：OpenAI / DeepSeek / Kimi / Qwen 多渠道，按优先级路由，
    第一个可用者胜出，全部失败则回落 Mock 引擎；
  - 每个渠道独立配置 base-url / model / 温度 / 超时，密钥只从环境变量读入；
  - 管理台可见：供应商健康度、最近调用与失败原因。
- **视觉**：左边供应商列表（带健康状态灯），中间"路由 + 超时 + 重试"，
  右边规划引擎；用一条虚线标出"任一步失败都有兜底"。
- **口播（≈40s）**：讲清"不绑定单一厂商"是**工程决策**：
  成本、可用性、合规备份，任何一家出问题演示都能继续。

### 第 10 页 · 工具分层：谁实时、谁兜底、谁计算

- **屏幕文字**（表格，三列）：

| 工具 | 能力 | 在系统里负责 |
| --- | --- | --- |
| 12306 MCP | 车次、余票、票价、经停、中转 | 跨城交通方案 |
| 百度地图 Web 服务 | POI、路线、距离耗时、逆地理 | 市内接驳与地图底图 |
| Open-Meteo | 天气、降水、风速 | 出行可行性与雨天替代 |
| 内容库参考价 | 门票参考价、开放时间 | 兜底与来源标注 |

- **视觉**：表 + 右侧一张"统一工具返回结构"的代码小框：
  `data / source / queriedAt / isRealtime / isCached / isMock / expiresAt`。
- **口播（≈40s）**：所有工具走同一层适配，
  因此界面能**如实**显示"这条数据是实时还是演示"，
  以及"失败原因是什么"。

### 第 11 页 · 核心竞争力：可执行性校验

- **屏幕文字**（生成后逐项核对）：
  - 景点是否在开放时间内；
  - 节点之间是否时间冲突、路线耗时是否合理；
  - 是否预留步行与换乘时间；
  - 每日景点数是否过量（行程强度：轻松 / 适中 / 紧凑）；
  - 预算是否超限；天气是否影响户外安排；车次是否可用。
  结论句：**先回答"为什么这个方案走得通"，再谈文案好不好看。**
- **视觉**：左侧一张行程时间轴截图，右侧校验结果清单
  （通过 = 青，风险 = 朱），底部放一行对比：
  "AI 直出方案 vs 校验后方案"。
- **口播（≈45s）**：这是本项目的差异化，建议配合演示视频或现场操作。

### 第 12 页 · 内容与运营：管理台

- **屏幕文字**：
  - 景区内容维护：图文、坐标、开放时间、票价、图片来源与授权登记；
  - 资源上传：管理台上传图片 / APK，不写死在代码里；
  - 运营配置：首页推荐位、主题路线、文化锦囊、工具配额与限流阈值；
  - 版本发布：调试 / 正式双通道，含更新说明与强制更新跨度。
- **视觉**：管理台截屏 2 张（景点管理 + 版本发布），
  在旁边用一个小流程图标出"运营改内容 → APK 立即生效，不必重新发包"。
- **口播（≈35s）**：这段回应"数据从哪来、谁维护、怎么更新"。

### 第 13 页 · 社区与足迹：行后沉淀

- **屏幕文字**：
  - 图文旅记发布与编辑（作者修改后回到待审核）；
  - 点赞 / 收藏 / 评论 / 二级评论 / 评论点赞 / 举报；
  - 收藏总站：景区、帖子、行程三类可切换；
  - 足迹：河南地图点亮去过的城市 + 里程、天数统计。
- **视觉**：社区信息流卡片（作者栏 / 封面 / 互动栏）+ 足迹地图各一张。
- **口播（≈30s）**：说明社区是"行后记录"，不与行前规划抢主次。

### 第 14 页 · 交互与视觉设计

- **屏幕文字**：
  - 主题：现代中原文化 × 山河旅行影像 × AI 智慧规划；
  - 交互原则：每个入口都能点到真实去处，不做"点了不动"的占位；
  - 反馈原则：加载、空、错误、缓存、过期五态齐全，弱网不白屏；
  - 适配：Android 10+ 常见中端机型，360×800 / 390×844 / 412×915 三档布局回归。
- **视觉**：三屏并排（首页 / 行程 / 我的），旁边列动效时长
  （反馈 120–160ms，面板 240–320ms）与"支持减少动效"。
- **口播（≈30s）**：强调"不是套模板"：色彩、间距、状态都是自己定的 token。

### 第 15 页 · 数据安全与隐私合规

- **屏幕文字**：
  - 密码 BCrypt 哈希；JWT 双令牌（访问 + 刷新）；用户 / 运营 / 管理员分权；
  - 行程与收藏做归属校验，防水平越权；接口全量参数校验；
  - 第三方密钥只存服务端环境变量，APK 内不含任何密钥；
  - 数据最小化：不采身份证、银行卡、支付信息，不后台持续定位；
  - 可删除：行程、收藏、账号、分享链接；日志不记录令牌与明文密码；
  - 限流：登录、验证码、AI 规划、外部工具配额均可在管理台配置。
- **视觉**：一页表格式"风险 → 措施"，配一张接口鉴权流程图。
- **口播（≈35s）**：直接点名"我们没做什么"，比只讲做了什么更可信。

### 第 16 页 · 测试与稳定性

- **屏幕文字**（项目当前实测数据）：
  - 后端单元 / 集成测试 **137 项通过**；
  - 客户端组件与布局测试 **163 项通过**，`flutter analyze` 0 issue；
  - 布局回归覆盖 360×800、390×844、412×915 三档；
  - 异常路径测试：外部工具超时、地图为空、车次无结果、LLM 返回格式错误、
    缓存过期、演示数据标识正确；
  - 安全测试：未登录访问、越权访问、过期令牌、SQL 注入、XSS、分享信息泄露。
- **视觉**：数字用大字；下方放"故障注入 → 降级表现"对照表三行。
- **口播（≈35s）**：一句话：**外部依赖全挂，演示仍然讲得完**。

### 第 17 页 · 推广价值与后续规划

- **屏幕文字**：
  - 对游客：把"查攻略 + 拼行程"从数小时压到几分钟，且行程可核对；
  - 对河南文旅：把分散的景区与交通信息，组织成可执行的旅行产品；
  - 可复制：走廊化的内容结构 + 工具适配层，换省即可复用；
  - 后续：实景授权图与演示视频、HTTPS 与正式签名 Release、
    更多走廊覆盖、行中实时能力增强。
- **视觉**：左侧价值三段，右侧"复制到其他省份需要改什么"的清单
  （内容库、走廊配置、地图与交通适配）。
- **口播（≈30s）**：讲商业与推广价值时保持克制，落到"结构可复用"上。

### 第 18 页 · 收尾

- **屏幕文字**：
  - 一句话总结：**豫见智旅不生成一段旅游文案，而是产出一份有依据、能调整、可执行、可分享的行程。**
  - 下方：仓库地址 / 演示账号 / 联系方式（二维码）。
- **视觉**：青黛底色 + 一行简介 + APK 图标，不放致谢套话堆叠。
- **口播（≈15s）**："以上是我们的作品，请评委老师提问。"

## 3. 问答预案

| 评委会问 | 建议回答要点 |
| --- | --- |
| 这和直接用大模型聊天有什么区别？ | 职责边界：模型只做理解与表达，规则校验、时间冲突、预算、强度计算都在后端；输出经过 Schema 校验后落库，不是一段文本。 |
| 数据是实时的吗？ | 分四态并如实标注：实时 / 缓存 / 系统资料 / 演示。12306 走 MCP 官方接口，天气走 Open-Meteo，地图走百度 Web 服务；不可用时降级并说明原因，绝不把演示数据说成实时。 |
| 为什么不用一个模型就够了？ | 成本、可用性与合规备份；多供应商按优先级路由，任一渠道故障演示不中断。 |
| 你们的创新点是什么？ | 可执行性校验（开放时间、接驳耗时、强度、预算、天气）+ 数据来源可视化 + 走廊化内容结构。 |
| 数据安全和隐私怎么保证？ | 见第 15 页：BCrypt、JWT、分权、归属校验、密钥服务端、数据最小化、限流配额、可删除。 |
| 项目有多少人几个月？分工？ | 如实回答：创意、交互、内容、联调由队伍完成，AI 工具用于辅助编码与测试，细节见《AI工具使用说明》。 |
